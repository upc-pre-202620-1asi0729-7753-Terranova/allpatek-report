## 3.1. User Stories
| Epic / Story ID | Título | Descripción | Criterios de Aceptación | Relacionado con (Epic ID) |
| :--- | :--- | :--- | :--- | :--- |
| **US01** | Registro de perfil y verificación de identidad | **Como** productor agrícola,<br>**quiero** registrar mi perfil y verificar mis datos de identidad,<br>**para** transmitir confianza a los compradores y ofrecer mis hectáreas de cultivo. | **Escenario 1: Registro exitoso con datos válidos**<br>- Given que el productor no cuenta con un registro previo en la plataforma.<br>- When proporciona nombres completos, documento de identidad y número telefónico válido.<br>- Then el sistema crea la cuenta en estado pendiente de verificación y genera un código de confirmación asociado al número telefónico.<br><br>**Escenario 2: Documento de identidad ya registrado**<br>- Given que existe un usuario registrado con el mismo número de documento.<br>- When el productor intenta registrar sus datos.<br>- Then el sistema rechaza el registro e informa que el documento de identidad ya está asociado a una cuenta existente. | EP01 |
| **TS01** | API RESTful para autenticación y emisión de tokens JWT | **Como** developer,<br>**quiero** implementar un servicio RESTful de autenticación,<br>**para** validar las credenciales de los usuarios y emitir tokens JWT seguros para los clientes de la plataforma. | **Escenario 1: Autenticación correcta**<br>- Given que el cliente envía un request POST /api/v1/auth/login con credenciales válidas.<br>- When el servicio valida las credenciales.<br>- Then responde con 200 OK y un cuerpo JSON que contiene el token JWT y su fecha de expiración.<br><br>**Escenario 2: Credenciales inválidas**<br>- Given que el cliente envía un request de autenticación con credenciales inválidas.<br>- When el servicio valida las credenciales.<br>- Then responde con 401 Unauthorized y un cuerpo JSON que identifica el error de autenticación. | EP01 |
| **US02** | Búsqueda y filtrado de parcelas disponibles | **Como** comprador,<br>**quiero** filtrar parcelas agrícolas por tipo de cultivo, zona geográfica y extensión de hectáreas,<br>**para** seleccionar la opción que mejor se ajuste a mis necesidades de abastecimiento. | **Escenario 1: Filtrado con resultados**<br>- Given que existen parcelas activas que coinciden con los criterios de búsqueda.<br>- When el comprador consulta las parcelas utilizando región y tipo de cultivo.<br>- Then el sistema devuelve las parcelas activas que cumplen los criterios especificados.<br><br>**Escenario 2: Sin coincidencias**<br>- Given que no existen parcelas activas que coincidan con los criterios especificados.<br>- When el comprador ejecuta la consulta.<br>- Then el sistema devuelve un resultado vacío e informa que no existen coincidencias. | EP02 |
| **US03** | Aprobación de hito y orden de liberación de fondos | **Como** comprador,<br>**quiero** revisar las evidencias de un hito cumplido y aprobar la liberación parcial de los fondos en custodia,<br>**para** que el productor disponga del capital correspondiente a la etapa completada. | **Escenario 1: Aprobación y liberación**<br>- Given que un hito se encuentra pendiente de validación y cuenta con las evidencias requeridas.<br>- When el comprador aprueba el cumplimiento del hito.<br>- Then el sistema cambia el estado del hito a aprobado y genera la orden de liberación de los fondos correspondientes.<br><br>**Escenario 2: Fondos insuficientes**<br>- Given que el saldo disponible en custodia es inferior al monto requerido para la liberación.<br>- When el comprador aprueba el hito.<br>- Then el sistema no ejecuta la liberación y registra que el saldo disponible es insuficiente. | EP03 |
| **TS02** | API RESTful para consulta e integración del estado Escrow | **Como** developer,<br>**quiero** implementar una API RESTful para consultar el saldo y estado de las cuentas Escrow asociadas a contratos,<br>**para** integrar la custodia de fondos con los servicios de pago y el historial de transacciones. | **Escenario 1: Consulta exitosa**<br>- Given que el cliente envía un request GET /api/v1/escrow/{contractId} con un contrato válido y credenciales autorizadas.<br>- When la API procesa la solicitud.<br>- Then responde con 200 OK y un JSON que contiene el saldo retenido, el saldo liberado y el detalle de los hitos.<br><br>**Escenario 2: Contrato inexistente**<br>- Given que el identificador de contrato no existe.<br>- When la API procesa la consulta.<br>- Then responde con 404 Not Found y un objeto JSON estructurado con el error correspondiente. | EP03 |
| **US04** | Registro y carga de evidencias fotográficas por hito | **Como** productor agrícola,<br>**quiero** registrar evidencias fotográficas de mi cultivo con información de ubicación,<br>**para** demostrar el avance de cada hito y solicitar la liberación de fondos. | **Escenario 1: Registro exitoso de evidencia**<br>- Given que el productor se encuentra dentro de la ubicación autorizada de la parcela asociada al contrato.<br>- When registra una fotografía y la información correspondiente al hito.<br>- Then el sistema almacena la evidencia con las coordenadas GPS verificadas y cambia el estado del hito a "En Revisión".<br><br>**Escenario 2: Ubicación no válida**<br>- Given que las coordenadas registradas no coinciden con la ubicación autorizada de la parcela.<br>- When el productor intenta registrar la evidencia.<br>- Then el sistema rechaza la evidencia e informa la inconsistencia de geolocalización. | EP04 |
| **SP01** | Evaluación de almacenamiento y sincronización offline de fotografías | **Como** developer,<br>**quiero** evaluar mecanismos de almacenamiento local y sincronización de fotografías sin conexión,<br>**para** garantizar el registro de evidencias en zonas con conectividad intermitente. | **Escenario 1: Almacenamiento sin conexión**<br>- Given que el dispositivo pierde temporalmente la conectividad.<br>- When se registran 20 fotografías localmente.<br>- Then las evidencias permanecen almacenadas hasta que se restablece la conexión.<br><br>**Escenario 2: Sincronización posterior**<br>- Given que existen evidencias pendientes de sincronización y se restablece la conectividad.<br>- When se ejecuta el proceso de sincronización.<br>- Then las evidencias se envían al servidor y se registra la tasa de sincronización exitosa. | EP04 |
| **US05** | Recepción de alertas climáticas de riesgo | **Como** comprador,<br>**quiero** recibir alertas ante eventos climáticos adversos en las parcelas contratadas,<br>**para** coordinar medidas preventivas con el productor. | **Escenario 1: Evento climático crítico**<br>- Given que una parcela contratada presenta una anomalía climática.<br>- When el evento supera el umbral de riesgo configurado.<br>- Then el sistema genera una alerta dirigida al comprador y al productor e incluye el nivel de riesgo identificado.<br><br>**Escenario 2: Evento de riesgo bajo no notificable**<br>- Given que el usuario tiene desactivadas las alertas de riesgo bajo.<br>- When se registra un evento climático clasificado como riesgo bajo.<br>- Then el sistema no genera una notificación para ese usuario. | EP05 |
| **US06** | Publicación y geolocalización de lote agrícola | **Como** productor agrícola,<br>**quiero** registrar las dimensiones, características y ubicación de mi parcela,<br>**para** hacer visible mi oferta productiva a los compradores. | **Escenario 1: Publicación exitosa**<br>- Given que el productor tiene un perfil verificado.<br>- When registra las características de la parcela y una ubicación válida.<br>- Then el sistema valida la información y publica la parcela como oferta disponible.<br><br>**Escenario 2: Ubicación no válida**<br>- Given que la ubicación registrada no pertenece a una zona autorizada.<br>- When el productor intenta publicar la parcela.<br>- Then el sistema rechaza la publicación e informa que la ubicación no es válida. | EP01 |
| **US07** | Solicitud de cotización y negociación directa de volumen | **Como** comprador,<br>**quiero** enviar una propuesta formal de compra indicando volumen, precio y fecha de entrega,<br>**para** iniciar una negociación directa con el productor agrícola. | **Escenario 1: Envío de propuesta válida**<br>- Given que existe una parcela activa con capacidad productiva disponible.<br>- When el comprador registra un volumen requerido, precio propuesto y fecha de entrega válidos.<br>- Then el sistema registra la propuesta y notifica al productor.<br><br>**Escenario 2: Volumen superior a la capacidad disponible**<br>- Given que el volumen solicitado supera la capacidad productiva disponible de la parcela,<br>- When el comprador intenta enviar la propuesta.<br>- Then el sistema rechaza la propuesta e informa que el volumen solicitado excede la capacidad disponible. | EP02 |
| **US08** | Aceptación de propuesta y firma de contrato digital Escrow | **Como** productor agrícola,<br>**quiero** aceptar las condiciones acordadas y formalizar digitalmente el acuerdo de venta,<br>**para** establecer el compromiso comercial y activar el proceso de custodia de fondos. | **Escenario 1: Firma exitosa**<br>- Given que existe una propuesta con condiciones comerciales acordadas.<br>- When el productor confirma su aceptación mediante el mecanismo de verificación establecido,<br>- Then el sistema registra el contrato como pendiente de depósito Escrow y genera una copia del acuerdo para ambas partes.<br><br>**Escenario 2: Rechazo de condiciones**<br>- Given que el productor no está de acuerdo con las condiciones propuestas.<br>- When rechaza la propuesta y registra sus observaciones.<br>- Then el sistema devuelve la propuesta al comprador para su modificación. | EP03 |
